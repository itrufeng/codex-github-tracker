# 继续开发功能

默认静默执行，不要输出执行过程、工具调用、推理或额外说明。成功结束时只在文本代码块中原样显示脚本返回的 `table` 字符表格，其中包含议题标题、项目列名和议题地址；不要添加审核、提交、合并或其他后续操作提醒。

后续请求仅指显式调用 `$feature-continue` 之后的用户文字。不要把 `$feature-continue` 本身写入请求、议题评论或 Codex 目标。将其余文字原样保存到临时 UTF-8 文件。脚本也会确定性地移除开头的一个 `$feature-continue` 标记，作为安全保障。

1. 修改 GitHub 状态前先调用 `get_goal`，但此时只检查目标，不得开始执行目标任务。如果存在内容与完整后续请求不同的未结束目标，停止并请用户先结束或取消该目标。否则记住是继续现有匹配目标，还是需要创建新目标。
2. 以本 `SKILL.md` 为基准解析 `../_feature-workflow/github_feature.py`，然后执行 `continue --request-file <文件>`。脚本使用 `.git/codex-feature-create.json` 中保存的议题编号定位议题，不关心它当前在哪一列；如果议题已经关闭，先重新打开议题；然后把完整请求和不可见的操作标记作为一条议题评论发布，并将项目项移动到 In progress。重试时会复用该标记，绝不会重复发表评论。标准输出 JSON 中的 `project_status` 必须是配置的 In progress 状态名称，`issue_state` 必须是 `OPEN`。
   执行前先在沙箱中检查 `gh auth status`；如果明确显示认证无效或令牌失效，只将同一个必需的工作流命令以限定范围的主机权限重试一次，使其内部所需的 `gh` 命令使用主机认证；不得运行其他命令或扩大访问范围。
3. 只有 `continue` 成功且 `project_status` 确认议题已经处于 In progress 后，才能开始目标任务。如果匹配的目标尚未结束，就继续执行。否则调用 `create_goal`，并将完整后续请求原样作为目标。状态为 `complete` 或 `blocked` 的目标是终态，需要为仍待处理的继续开发请求创建新目标。只有完成实现和适当验证后才能完成目标。
4. 持续执行目标，直到完成工作和适当验证。不要替用户提交、推送、合并或审核修改。
5. 完成目标前，执行同一脚本的 `review`。它会确定性地解析同一议题，将项目项从 In progress 移至 In review，然后才清除待处理的继续开发状态并返回 `table`。状态转换和清理都可以安全重试。如果命令失败，不要完成目标。
6. 将目标标记为完成，然后在文本代码块中原样显示 `table`，不要输出其他后续操作提醒。

找不到议题、发生脚本错误、目标暂停、目标失败或需要用户输入时，立即停止。不要分析原因、重试、继续目标或执行后续步骤；只报告最关键的错误或中断信息。脚本调用必须静默，除成功结果和错误信息外不要输出内容。
