# 创建功能

默认静默执行，不要输出执行过程、工具调用、推理或额外说明。成功结束时只在文本代码块中原样显示脚本返回的 `table` 字符表格，其中包含议题标题、项目列名和议题地址；不要添加审核、提交、合并或其他后续操作提醒。

功能请求仅指显式调用 `$feature-create` 之后的用户文字。不要把 `$feature-create` 本身写入请求、议题正文或 Codex 目标。将其余文字原样保存到临时 UTF-8 文件，不要用摘要替代。脚本也会确定性地移除开头的一个 `$feature-create` 标记，作为安全保障。

1. 生成清晰的议题标题摘要，最多 30 个 Unicode 字符，让用户看到后能回想起功能内容。标题只使用摘要，不添加分支名前缀。
2. 以本 `SKILL.md` 为基准解析 `../_feature-workflow/github_feature.py`，然后执行 `create --summary <摘要> --request-file <文件>`。脚本会确定性地识别当前 GitHub 仓库和项目。对于新请求，它会创建议题、加入项目、显式移至 Ready，再移至 In progress，同时在 Git 本地状态中保存议题编号和 Ready 步骤完成标记；不要假设新项目项具有任何初始状态。如果已有待处理状态，脚本只会在验证仓库、项目、网址和完整正文都与本次请求一致后，按已保存的议题编号恢复并补齐尚未完成的状态步骤；绝不能根据摘要搜索。读取标准输出的 JSON：
   - `created`：已创建新议题。
   - `resumed`：已恢复现有议题。
   - `project_status`：必须是配置的 In progress 状态名称。

   执行前先在沙箱中检查 `gh auth status`；如果明确显示认证无效或令牌失效，只将同一个必需的工作流命令以限定范围的主机权限重试一次，使其内部所需的 `gh` 命令使用主机认证；不得运行其他命令或扩大访问范围。
3. 只有 `create` 成功且 `project_status` 确认议题已经处于 In progress 后，才能协调或开始 Codex 目标；不得提前调用 `get_goal` 或 `create_goal`。然后调用 `get_goal`：如果没有未结束的目标，就调用 `create_goal`，并将完整功能请求原样作为目标。如果未结束目标的内容与请求完全一致，继续该目标，不要重复创建。如果未结束目标的内容不同，停止并请用户先结束或取消该目标；不要替换它。状态为 `complete` 或 `blocked` 的目标不能恢复：为这个仍待处理的功能创建新目标。只有完成实现和适当验证后才能完成目标，不得仅因时间或预算不足而完成。
4. 分支不是本工作流的一部分，不检查、创建、切换或记录分支；即使当前使用 `main` 或 `master` 也可以继续。
5. 持续执行目标，直到完成实现和适当验证。不要替用户提交、推送、合并或审核修改。
6. 完成目标前，执行同一脚本的 `review`。它使用本地保存的议题编号，将项目项从 In progress 移至 In review，并返回 `table`。如果命令失败，不要完成目标。
7. 将目标标记为完成，然后在文本代码块中原样显示 `table`，不要输出其他后续操作提醒。

遇到任何异常、脚本错误、目标暂停、目标失败或需要用户输入，立即停止。不要分析原因、重试、继续目标或执行后续步骤；只报告最关键的错误或中断信息。脚本调用必须静默，除成功结果和错误信息外不要输出内容。
